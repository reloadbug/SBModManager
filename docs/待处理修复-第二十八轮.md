# 第二十八轮：下载管理 —— 按冲突自动装、批量确认、暂停/继续/彻底删除

> 用户反馈（原文）：
>
> > 多套文件不冲突的直接全部安装；冲突的才要选；下载管理顶部的工具按钮始终在最上面不随滚动消失；
> > 下载按钮做的更全面一些，支持批量确认，有多个文件时每组冲突的 mod 都默认选中第一个文件；
> > 不要手工一个一个确认；增加全部停止按钮；每个 mod 可以暂停，取消，继续下载，彻底删除等操作；
>
> 附截图：下载管理页，一条多变体包的任务停在「需要确认」，卡片右侧只有一个「确认安装」按钮。

拆成 7 件事，本轮全部实现：

| # | 需求 | 落点 |
|---|---|---|
| 1 | 互不冲突的多套内容**直接全装**，只有冲突才让用户选 | `installer.js` + `downloadEngine.js` |
| 2 | 下载管理顶部工具条**吸顶**，不随滚动消失 | `style.css` 的 `.dl-bar` |
| 3 | 下载/确认按钮**更全面**，支持**批量确认** | `app.js` + `ipc.js` 新增 `confirmAllDefault` |
| 4 | 多文件时**每组冲突默认选中第一个文件** | `installer.js` 的 `defaultPickOf` |
| 5 | **不要手工逐个确认** | 上面 1+3+4 合起来的效果 |
| 6 | 增加「**全部停止**」按钮 | `engine.pauseAll` + `app.js` |
| 7 | 每个 mod 支持**暂停 / 取消 / 继续 / 彻底删除** | `paused` 状态 + `pause/cancel/purge` |

## 一、先定两个不可逆操作的口径（问过用户再动手）

有两处是**删东西 / 停任务**，做错了没法回头，所以实现前先确认：

| 提问 | 用户选择 | 后果 |
|---|---|---|
| 「彻底删除」删到哪一步？ | **只删本地，不动游戏** | 队列记录 + 本地安装包 + 半截下载 + 缓存图全清；游戏目录里已装的文件**一个不碰**（那个归「已安装 Mod」页的「卸载」管，它会还原被覆盖的原始文件） |
| 「全部停止」是取消还是暂停？ | **暂停，保留进度** | 半截 `.part` 全留着，之后点「全部恢复」接着下，不重跑流量 |

这两条决定了下面所有实现。

## 二、需求 1 + 4：不冲突就全装，冲突才选，且每组默认第一个

### 问题根源：`needsTargetPick` 被当成了「必须让用户选」

一个归档里可能装着**多套互相替换的内容**（同一个角色的不同服装、同一把武器的不同贴图），
每套放在各自的子目录里。老代码识别出「这是多变体包」就直接把任务置成「需要确认」，
逼用户打开对话框挑 —— 哪怕这些内容**根本不冲突**，本来可以一起装。

### 判定「冲突」的口径

先给每套内容算一个**资产键**：

* 目录名里能抠出游戏资产 ID（如 `ID77117`）→ 用它
* 抠不出来 → 退化成 `name:<文件名>`

**键相同 = 同一件东西**，装两套就是一前一后互相覆盖。把所有套内容按「键相同」做**并查集分组**，
得到的就是互斥组：

```js
// installer.js
const groups = exclusiveGroups(options);      // 互斥组；组内只能选一套
const hasConflicts = groups.length > 0;       // ← 唯一的「要不要选」判据
```

### 默认选择集 `defaultPick`

规则一句话：**每个互斥组取第一套，不在任何组里的全选**。

```js
function defaultPickOf(options, groups) {
  const pick = [];
  const grouped = new Set();
  for (const g of groups) { pick.push(g[0]); for (const d of g) grouped.add(d); }  // 每组第一套
  for (const o of options) if (o && o.dir && !grouped.has(o.dir)) pick.push(o.dir); // 其余全选
  return pick;
}
```

> ⚠️ 这个口径有**两份实现**：主进程 `installer.js::defaultPickOf()` 与渲染层
> `app.js::openVariantPicker()` 里那句 `state.pick.add(g[0])`。两处必须逐条一致 ——
> 否则「一键安装」装出来的组合和用户打开对话框看到的勾选不一样。
> `variant-auto-test.js` 有专门的断言盯着这一点。

### 自动全装

`installPhase()` 在「识别失败 / 需要挑目标」的分支前，插了一段自动全装：

```js
if (plan && plan.needsTargetPick && !plan.diagnosis
    && opts.length && plan.hasConflicts === false && !_autoPicked) {
  const dirs = plan.defaultPick.length ? plan.defaultPick : opts.map(o => o.dir);
  return installPhase(id, { auto, onConflict, pickDirs: dirs, _autoPicked: true });
}
```

三个细节，都是踩过的：

* **`plan.hasConflicts === false` 用的是严格等号**。老任务落盘的计划里没有这个字段，
  值是 `undefined` —— 走不进自动全装，安静地回落到人工确认。用 `!plan.hasConflicts`
  就会把老计划当成「不冲突」直接装，那是错的。
* **`!_autoPicked` 防套娃**：递归调用时带上 `_autoPicked: true`，
  万一 `defaultPick` 算出来还是走这条分支，不会无限递归。
* **`!plan.diagnosis`**：带诊断信息的是**真出错**（压缩包坏了之类），不走自动装。

## 三、需求 2：顶部工具条吸顶

`.body` 是滚动容器、自带 `padding:16px`。工具条要吸顶并且**背景盖住滚上来的内容**：

```css
.dl-bar{
  position:sticky; top:-16px; z-index:18; background:var(--bg);
  /* 负 margin 抵消 .body 的 16px padding；再用 padding 补回内边距 */
  margin:-16px -16px 13px;
  padding:14px 16px 11px; border-bottom:1px solid var(--border);
}
```

两个必须同时满足的点：

* **`top:-16px` 与 `margin:-16px` 是一对**。sticky 是相对 **margin box** 生效的，
  只写 `top:0` 的话元素会停在离顶 16px 的地方，滚动时上面漏出一条缝。
* **背景必须不透明**。`background:var(--bg)` 不能省，否则滚上来的卡片会透过工具条显形。

顺带给底部加了一条纯装饰渐变线（`::after`，hover 时浮出来），滚动时能看出这是浮在上面的一层。

## 四、需求 3 + 5：批量确认，不用逐个点

### 单条：⚡ 一键安装

卡片上给「待确认」且**有默认选择集**的任务加了一个按钮，点一下按 `defaultPick` 装掉。
想改组合仍可点旁边的「选择内容」打开对话框。

主进程侧新增 `engine.confirmInstallDefault(id)`；老计划缺 `defaultPick` 会先 `planOf()` 补算。

### 批量：⚡ 一键安装全部

`ipc.confirmAllDefault()` 只挑 `status === 'needs_review'` 且**没有诊断信息**的任务，
**串行**执行，每条之间留 120ms（默认 `gapMs`）—— 每条都要解压分析，一口气并发会把磁盘打满。

界面上用按钮文案当进度条 + `download:confirmprogress` 事件实时回推，
完成后 toast 汇报「处理 N 项 / 失败 N / 仍有 N 项需要你挑内容」。

## 五、需求 6 + 7：暂停 / 全部停止 / 取消 / 继续 / 彻底删除

### 新增 `paused` 状态

`paused` 与 `interrupted` **语义不同**，别混：

| 状态 | 谁造成的 | 进不进「可恢复」集合 |
|---|---|---|
| `paused` | 用户主动点「暂停」/「全部停止」 | 进 |
| `interrupted` | 管理器被强杀、任务没跑完 | 进 |
| `cancelled` | 用户主动「取消」 | 不进（磁盘上什么都不该剩） |

`paused` 进 `TERMINAL`（终态，状态机不再自己动它），但**不进** `ACTIVE_DUPLICATE_STATUSES`
（再点一次「下载」不该被当成重复任务挡掉）。

### 「全部停止」只动这三种状态

```js
const PAUSABLE = new Set(['queued', 'resolving', 'downloading']);
```

**不含 `analyzing` / `installing`** —— 这两步正往游戏目录写文件，半途停下会在那里留半成品。

### 暂停留 `.part`、取消清 `.part`

用户的口径是「暂停 = 保留进度」。所以两者对半截文件的处理**正好相反**：

```js
function pause(id){ c.cancelled = true; c.keepPartial = true;  patch(id,{status:'paused', error:null}); }
function cancel(id){ c.cancelled = true; c.keepPartial = false; removePartsOf(t); }
```

`keepPartial` 一路透传到 `nxm.js::downloadToFile()` 的中止分支：

```js
cleanup(cancelled && !keepPartial);   // 取消才删，暂停绝不删
```

> 半截文件名是 `.dl-<modId>-<fileId>.part`，**故意不带时间戳** ——
> 恢复时要能按同样的名字找回上一次那半截。

### 中止状态不被回写（`settleAbort`）

`run()` 的中止分支原本无条件 `patch(id, {status:'cancelled'})`，
会把用户刚点的「暂停」冲成「已取消」。收敛函数保护这两种用户意图：

```js
function settleAbort(id){
  const cur = queue.get(id);
  if (!cur) return;
  if (cur.status === 'paused' || cur.status === 'cancelled') return;   // 用户说了算
  patch(id, { status: 'cancelled' });
}
```

### 彻底删除（`engine.purge`）清五面，**不动游戏**

1. 下载队列里的这条记录
2. 本地安装包（`.zip` 等）
3. 没下完的半截文件
4. `images/<modId>/` 下的缓存封面与预览图
5. 内存里的授权记录

界面上是**二次确认弹框**、按钮标红（`danger: true`）。弹框里那句
「彻底删除不会动游戏目录里的文件 —— 想卸载请到「已安装 Mod」页点「卸载」」
是刻意写给用户看的：免得有人以为「彻底删除」能卸掉游戏里的 mod。

> 删缓存图时逐个文件删、再删空目录 —— 绕开沙箱 safe-delete 的 50 文件阈值。

### 「全部恢复」的口径统一（修掉一个真 bug）

工具栏「全部恢复（N）」的**计数**与点击后的**实际恢复范围**原本各写各的：
计数已经含 `paused`，点击却还是手抄的 `interrupted || failed` ——
会出现「按钮写着（3），点下去只恢复 1 条」。现在两处都走同一个集合：

```js
const DL_RESUMABLE = new Set(['interrupted', 'failed', 'paused']);
```

`resume-download-test.js` 新增了断言盯这一点（两边各出现一次 `DL_RESUMABLE.has(...)`）。
