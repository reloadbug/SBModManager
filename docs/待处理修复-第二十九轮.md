## 一、先定三个口径（都问过用户再动手）

这三件事都有多种合理做法，做错了要返工，所以先确认：

| 提问 | 用户选择 | 具体含义 |
|---|---|---|
| 「已安装页的排序」怎么给？ | **加一排排序按钮** | 不是藏在设置里，也不是只有默认一种 —— 顶部直接摆出一排可点的按钮，当前生效的高亮 |

## 二、需求 1：已安装页不再列「待确认」

### 问题：同一批任务在两个页面各列一遍

已安装页顶部的实时条（`liveStrip()`）原来把 **`DL_BUSY` 里的在跑任务**和
**「待确认 / 安装失败但包还在」这类等用户操作的任务**混在一起列。于是同一批任务：

* 在已安装页：能看见，但只能看着
* 在下载页：也有，而且带原因解释和「⚡ 一键安装 / 去处理」按钮

用户得在两个页面之间来回找，还得自己判断「以哪个为准」。用户的原话是
「都统一在下载页面处理」—— 那就把实时条**收敛成只干一件事**：

```js
function liveStrip() {
  const busy = all.filter(t => DL_BUSY.has(t.status));   // ← 只有「正在跑」
  if (!busy.length) return '';
  ...
}
```

`DL_BUSY = new Set(['queued', 'resolving', 'downloading', 'analyzing', 'installing'])`。
**「等用户操作」的两种状态刻意不在里面**：

* `needs_review`（等你确认装哪些内容）
* `failed && archivePath`（装失败了、但安装包还在，可以重试）

它们不是「在跑」，列进来只会让人以为进度条卡住了。

> 原因解释逻辑**没有丢**，只是搬了家：下载页的 `taskWhy()` 负责说明「为什么停在待确认」，
> 卡片上还有具体的错误行。实时条的价值就剩下「不用切页也能看到进度」。

## 三、需求 2 + 3：排序与合并

### 3.1 先合并，再排序

渲染流程固定成三步，顺序不能换：

```js
state.installedGroups = groupInstalled(visible);                       // ① 按 modId 合并
const sorted = state.installedGroups.slice()
  .sort((a, b) => compareInstalled(a, b, state.installedSort));        // ② 排序
area.innerHTML = liveStrip() + `<div class="ibar">${sortBar}${toggleRow}</div>`
  + `<div class="grid">${sorted.map(installedCard).join('')}</div>`;   // ③ 画卡
```

**必须先合并再排序**：排序的对象是「卡片」，不是磁盘上的文件条目。
要是先排条目再合并，同一个 Mod 的几个文件会被别的 Mod 隔开，合并出来的卡片顺序就没有意义了。

侧栏计数也跟着换口径 —— 显示的是**合并后的卡片数（= Mod 数）**，不是磁盘条目数：

```js
function syncInstalledNav() {
  const gs = groupInstalled(state.installed).filter(g => !g.builtin);
  el.textContent = gs.length;
}
```

> ⚠️ `state.installed` 本身**始终是磁盘扫描出来的原始条目**（启用数、卸载都按原始项走）。
> 图表上画的是分组后的卡片 —— 这两个口径不要混。

### 3.2 `groupInstalled()`：合并依据只有 modId

```js
const modId = Number(src.modId || (m.meta && m.meta.modId) || 0) || 0;
const key = modId ? ('mod:' + modId) : ('one:' + m.id);
```

* **有 modId 的** → 同一个 Mod 的多个已安装文件合成一张卡（`key = mod:<modId>`）
* **没有 modId 的**（手动丢进 `~Mods`、未登记的）→ **各自一张卡**（`key = one:<id>`）

第二条是刻意的：手上没有任何依据能证明这几个目录属于同一个东西，硬并就是瞎猜。

组对象**刻意做成与单个 installed 项同形**（`id / name / kind / enabled / size / files / meta …`），
这样 `installedCard()` 和 `openInstalledDrawer()` 不用大改；多出来的 `items` 才是
「这个 Mod 装了哪几个文件」。

几个聚合字段：

| 字段 | 口径 |
|---|---|
| `name` | 取「**带来源信息**」的那条（`meta.name` 或 `meta.source` 存在）的 `name`，没有才用第一条 |
| `enabled` | 组内**至少一个**启用 → `true` |
| `partial` | 有启用也有禁用 → `true`（**部分启用**，开关画成第三种状态） |
| `size` / `fileCount` | 组内求和 |
| `files` | 组内 `flatMap` 合并 |
| `mtime` | 组内**最「新」**的那条（空 mtime 不算） |

### 3.3 `compareInstalled()`：每个模式都带兜底键

用户给的口径是「**优先按时间，其次按摩的的，mod 名称**」——这是一条**全序**规则，
不是「只按时间」。所以每个模式都必须能分出先后，否则 `Array.sort` 的比较函数
在相等时返回 0，顺序就取决于引擎内部实现，同一份数据两次渲染可能不一样。

| 模式 | 主键 | 兜底键 1 | 兜底键 2 |
|---|---|---|---|
| `time`（默认） | 组 mtime **倒序** | Mod ID 升序 | 名称升序 |
| `name` | 名称升序 | Mod ID 升序 | — |
| `modid` | Mod ID 升序 | 名称升序 | — |
| `kind` | 前置组件 → Pak / 逻辑模组 → 脚本 | 名称升序 | Mod ID 升序 |

两个细节：

* **`time` 是倒序**（`at < bt ? 1 : -1`），其余都是升序 —— 用户要的是「最新的在最上面」。
* **没有 modId 的排在最后**：

  ```js
  const av = a.modId || 0, bv = b.modId || 0;
  if (av === bv) return 0;
  return (av || Infinity) - (bv || Infinity);
  ```

  `0 || Infinity` → `Infinity`，所以手动包永远沉底。否则它们会插在 Nexus 来源的中间，
  位置随扫描顺序乱跳 —— 用户会以为排序坏了。

* `kind` 的排名表在 `KIND_RANK`：`{ prereq: 0, pak: 1, logicmod: 1, script: 2 }`，
  表里没有的类型落到 `?? 3`（排最后）。**逻辑模组与 pak 同级** —— 它们都是「已安装的实体模组」。

### 3.4 卡片：三态开关 + 角标

合并后的卡片带 `data-gid="<组键>"`，点击开的是「**这个 Mod**」，不是某个文件。
开关有三个状态（`sw` / `sw off` / `sw part`），`part` 就是「部分启用」：

```js
`<button class="sw${g.enabled ? '' : ' off'}${g.partial ? ' part' : ''}"
         data-gtoggle="${esc(g.key)}"></button>`
```

**前置组件不给开关**（`g.kind === 'prereq' ? '' : ...`）—— 它的存在是别的 Mod 能跑的前提。

多文件时封面上多一个角标「N 个已装文件」。它被挪到**左下角**，
因为右下角被这轮新加的 👍/👎 占了位置（见第五节）。

### 3.5 抽屉：逐文件可操作

抽屉里多了一段「已安装的文件（N 个，可逐个操作）」，每行是一个文件：

```js
`<button class="btn sm" data-iid="${esc(it.id)}" data-iact="toggle">禁用</button>
 <button class="btn sm d"  data-iid="${esc(it.id)}" data-iact="uninstall">卸载</button>`
```

> **逐文件操作不需要动主进程**：`mods:setEnabled` / `mods:uninstall` 本来就是按
> **单条 id** 定位的（重新 `scanner.scan()` 后 `list.find(m => m.id === id)`）。
> 这里传的是单条 installed 项的 `id`，不是组键。

前置组件那一行只显示一句说明，不给按钮：

> 前置组件，不可单独禁用或卸载

抽屉底部的按钮则是**整组作用**（`data-gtoggle` / `data-guninstall`），文案会带数量，
并在 `title` 里写明作用范围。

### 3.6 组级开关是三态，别写成两态

```js
async function doToggleGroup(key) {
  const g = groupOf(key);
  const target = g.partial || !g.enabled;   // ← 关键这一句
  ...
}
```

**不能只写 `!g.enabled`**。部分启用时 `enabled` 已经是 `true`，`!g.enabled` 是 `false`，
于是按钮在「部分启用」状态下点下去没有任何反应 —— 用户会觉得按钮坏了。

组级卸载是**逐条**调的，失败不中断：

```js
async function doUninstallGroup(key) {
  for (const it of g.items) { try { await call(window.api.mods.uninstall(it.id)); ok++; }
                              catch { bad++; } }
  // 最后统一报数：两条 toast 各自成句（不拼接，否则多语言下会中英混排）
}
```

卸载后 `reopenInstalledDrawer(key)` 重建抽屉；**最后一个文件也卸掉就关抽屉**
（留着会显示一个空壳）。

## 四、需求 6：👍 / 👎 纯图标按钮

### 4.1 为什么不用 emoji

用户要求「不显示文字，只显示两个图标，大拇指向上，大拇指向下」。
最直接的做法是写 `👍` / `👎` 两个字符 —— 但**在 Windows 上不行**：
彩色 emoji 的「点亮 / 未点亮」几乎看不出区别（`color` 对彩色 emoji 无效），
用户根本不知道自己是点过还是没点过。

所以用**内联 SVG + `currentColor`**：图标跟随 `on` 类整体变色，
未点亮是灰的、点亮是绿的 / 红的，一眼可辨。

```js
function voteHtml(n) {
  const liked   = state.browse.liked.has(String(n.modId));
  const blocked = state.browse.blocked.has(String(n.modId));
  return `<div class="vote">
    <button class="vbtn up${liked ? ' on' : ''}" ${
      liked ? `data-unlike="${n.modId}"` : `data-like="${n.modId}"`}>${ICON_THUMB_UP}</button>
    <button class="vbtn down${blocked ? ' on' : ''}" ${
      blocked ? `data-undislike="${n.modId}"` : `data-dislike="${n.modId}"`}>${ICON_THUMB_DOWN}</button>
  </div>`;
}
```

属性名同时也是**状态机的开关**：已喜欢时给的是 `data-unlike`（再点一次=取消），
未喜欢时给 `data-like`。点击处理里靠属性名分流，不需要额外判断。

两件事**独立**，不是二选一：喜欢一个 Mod 不会把它从黑名单移出来，反之亦然。
按钮**文字消失**，但 `title` 还在（鼠标悬停能看到「喜欢 —— 可以用「只看喜欢」筛出来…」）。

### 4.2 `favorites.js` 与 `blacklist.js` 完全对称

```js
add(id, meta)   // 幂等：重复点只更新时间戳，保留原 at
remove(id)      // 不在名单里返回 null，不抛
all() / ids() / has(id) / count() / clear()
```

记下 `name / author / thumbnail` 是为了「只看喜欢」视图能**离线渲染卡片**（零网络请求）。

> **为什么不合并成一个文件、加个 `kind: 'liked' | 'blocked'` 字段**：
> 两者语义相反（一个隐藏、一个收藏），将来行为会分叉
> （「喜欢」可能同步到 Nexus 收藏夹，「黑名单」永远不会）。
> 现在共用一个文件，反而会在分叉时被迫做数据迁移。
> `favorites-test.js` 里有一条专门的「对称性」断言：两边的 `add()` 返回字段名必须完全一致。

### 4.3 「只看喜欢」：与「只看黑名单」共用一条本地视图

原来的 `loadBlockedList()` 泛化成 `loadLocalList(reset, kind)`，`kind` 取 `'blocked' | 'liked'`：

```js
if (b.onlyLiked) return loadLocalList(reset, 'liked');
if (b.blockMode === 'only') return loadLocalList(reset, 'blocked');
```

**为什么这两条不走 Nexus 分页**：黑名单 / 喜欢通常只有几条到几十条，
而 Nexus 有 3000+ 个 Mod。「翻页 + 过滤」要翻遍全站才凑得出来（一次 24 个，翻 20 页也才 480 个）——
用户点「只看黑名单」得等半分钟还看不到东西。本地记录里有 name/author/thumbnail，
零网络请求，秒开。

两个视图**互斥**：一个列表里不可能既只留喜欢的、又只留拉黑的。
点其中一个会自动把另一个关掉。

### 4.4 「喜欢的排前面」= 稳定置顶，且不隐藏任何东西

```js
if (b.liked.size) {
  const rank = (m) => (b.liked.has(String(m.modId)) ? 0 : 1);
  kept = kept.slice().sort((x, y) => rank(x) - rank(y));
}
```

* 只是**重排**，没有任何 `filter` —— 喜欢的 Mod 不会把别的挤掉（与黑名单的语义正好相反）
* 用 `slice()` 复制再排，不动调用方那个数组
* 没有喜欢时**原样返回同一个数组**（连切片都省了）
* `Array.sort` 在 V8 里是稳定的，所以「喜欢的那几个」和「其余的那些」各自保持原有相对顺序

> 代码注释里明确写了「**只是本页内**的置顶，不能承诺全站」——
> 避免后人误以为可以靠它把喜欢的 Mod 顶到整个列表最前面。

## 五、需求 4 + 5：点下载直接进后台（核实结论：已达，本轮无新代码）

截图里那个 Mod 「点下载后没反应 / 下载不了」，核对下来是**上一轮已经修好的那个 bug**
（`nexus.pickPrimaryFile` 的实例方法没挂上，导致现场补 fileId 时抛错），
本轮**没有新增代码**，只做了复核：

* `dlEnqueue(meta, { authorize = true })` **默认就走后台自动授权**
  （`download.autoAuthorize`）—— 不会打开浏览器、也不会弹内嵌助手窗口；
* 只有自动授权**失败**时才降级调 `download.authorize`（内嵌助手窗口，让用户手动点）；
* 入队时没有 fileId 的（浏览页卡片直点「下载」、批量下载时 `nexus.files()` 失败），
  `ipc.autoAuthorizeTask()` 会在 `fetchNxm` **之前**用 modId 现场查主文件补齐。

错误提示（需求 5）同样已具备：任务失败会带分类错误码，
下载卡片上用 `taskWhy(t)` 把「为什么停住 / 为什么失败」翻成人话。

> ⚠️ 这里有个历史上踩过的坑：老代码会把 `no_nxm` 一律说成「作者只开了手动下载」——
> 既**冤枉作者**，又没给用户任何退路。现在的口径是先按 fileId 失效自愈重试一次，
> 只有白名单里的死号错误码才走这条提示。
